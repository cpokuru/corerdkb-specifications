Values are current design targets

Flash Details

Why the flash floor is what it is, what every profile's layout must provide, and the storage technologies this specification recognizes -- generic across all profiles.

Why 4 GB? Two banks, not one

Flash minimums assume a dual-bank (A/B) layout for OTA, which requires roughly double the flash of an equivalent single-bank design (two full kernel + rootfs copies, not one). A safe firmware upgrade writes and verifies the complete new image into the passive slot before switching boot selection -- there is no reliable A/B upgrade path that shares space between active and standby images.

A/B banking applies to every OTA-relevant partition, not just RootFS -- Bootloader, Kernel/BootFS, and RootFS are all duplicated as full A-slot/B-slot pairs, each slot sized to the SAME capacity. If RootFS uses 500 MiB, the device needs capacity for TWO 500 MiB RootFS slots (1,000 MiB total for RootFS alone). Treating a single measured partition size as the full device flash requirement is the single most common flash-sizing error. The documented exception is NVRAM/persistent configuration, measured as a single shared partition rather than duplicated A/B -- configuration state doesn't need a standby copy the way an executable firmware image does.

Measured evidence:

Two separate storage-analysis reports (one per profile) confirm the current A/B layout already allocates ~2,172 MiB before metadata, so a 2,048 MiB (2 GiB) part does not fit it. Both reports independently converge on the same recommendation: 2 GiB insufficient, 4 GiB technical minimum, 8 GiB recommended production capacity.

Single-bank designs use less flash but have no standby image to fall back to, and MUST implement an alternative recovery mechanism (a dedicated recovery partition or a field-service reflash procedure) to achieve comparable OTA safety. See Section 3.1.1, Storage Conformance Modes.
